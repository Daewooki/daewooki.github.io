## 들어가며
2026년 8월을 전후해 OpenAI·Anthropic·Google이 공통적으로 “더 큰 모델”보다 **에이전트를 굴리기 위한 API 형태/운영 정책**을 빠르게 재정렬하고 있습니다. 특히 OpenAI는 Assistants API를 공식적으로 접고 Responses API로 수렴시키고, Google은 Gemini API Key 운영을 강제하며, Anthropic은 대형 컨텍스트/도구 생태계(MCP)를 전면에 밀어붙이는 흐름이 뚜렷합니다.[^1]

---

## 📰 무슨 일이 있었나
- **OpenAI (Assistants API → Responses API로 수렴)**
  - OpenAI Developer Community 공지에 따르면 **Assistants API beta는 2026년 8월 26일에 sunset**됩니다(공지 게시일: 2025년 8월 26일). 마이그레이션 경로로 **Responses API**를 명시했고, “feature parity에 도달했다”고 밝힙니다.[^1]
  - 같은 공지에서 Responses API는 code interpreter, persistent conversations를 포함하고, built-in tools로 **deep research, MCP, computer use** 등을 언급합니다(즉, “에이전트용 1-call primitive”를 표준으로 삼겠다는 메시지).[^1]
  - 참고로 OpenAI Help Center의 Model Release Notes에는 **o3가 2026년 8월 26일 ChatGPT에서 retired**된다는 내용이 있지만, 이는 “ChatGPT만 해당이며 API 변경은 없다”고 선을 긋습니다(날짜가 같아서 혼동 포인트).[^2]

- **Google (Gemini: Interactions API GA + Key 제한 강제)**
  - Google AI for Developers 문서에서 **Interactions API가 2026년 6월 기준 GA이며 신규 프로젝트에 권장**된다고 명시합니다. 특징으로는 서버 측 state 관리(예: `previous_interaction_id`)를 통해 상호작용을 누적하는 형태를 강조합니다.[^3]
  - Google AI Developers Forum 공지에 따르면 **2026년 6월 19일부터 Gemini API는 unrestricted API key 요청을 거부**합니다. 즉 “키를 제한(restrict)하지 않으면 서비스가 끊길 수 있는” 운영 정책 변경입니다.[^4]
  - 또한 Gemini API 입력 경로도 확장되어 **inline payload limit 20MB → 100MB**, GCS object registration, HTTPS/Signed URL 지원이 추가되었다고 Google 블로그가 설명합니다(발행: 2026년 1월 12일).[^5]
  - I/O 2026 개발자 하이라이트에서는 **Gemini 3.5 Flash**, “Managed Agents in the Gemini API” 등 에이전트 지향 업데이트를 전면에 배치합니다(발행: 2026년 5월 19일).[^6]

- **Anthropic (Claude Sonnet 5 + MCP 2026-07-28 수용 + 플랫폼 릴리즈노트 강화)**
  - Claude Platform release notes에 따르면 **Claude Sonnet 5(`claude-sonnet-5`) 출시**, **1M token context**, **max output 128k**를 명시하고, **intro pricing $2 / $10 per MTok(입력/출력) ~ 2026년 8월 31일까지** 제공한다고 적혀 있습니다.[^7]
  - Anthropic은 2026년 7월 28일자 블로그에서 **MCP 2026-07-28 spec(“stateless core”)을 Claude에 가져온다**고 밝혔습니다. 에이전트가 외부 tool/data에 붙는 표준을 “HTTP workload로 단순화”한다는 방향성이 핵심입니다.[^8]

---

## 🔍 왜 중요한가
1) **“API 형태”가 바뀌면, 아키텍처의 중심이 바뀐다**  
OpenAI의 Assistants → Responses 전환은 단순 endpoint 교체가 아니라, 제품 팀이 “에이전트의 표준 실행 단위”를 Responses로 못 박는 신호입니다. 앞으로 신규 기능(도구, multi-step, state 유지)이 Responses에 먼저(혹은 전용으로) 들어갈 가능성이 높고, Assistants 기반 구현은 **2026년 8월 26일 이후 운영 리스크가 확정**입니다.[^1]

2) **운영/보안 정책이 ‘옵션’에서 ‘강제’로**  
Google의 “unrestricted API key 차단”은 개발팀에 매우 실무적인 의미가 있습니다.  
- 키 발급/배포 프로세스(Secrets 관리)뿐 아니라  
- **테넌트별 키 분리, API restriction 설정, 장애 대응(runbook)**  
같은 SRE/플랫폼 작업이 곧바로 backlog로 떨어집니다. “모델 성능”과 무관하게, 이런 변경은 장애로 이어지기 쉬워서 더 위험합니다.[^4]

3) **에이전트 생태계는 ‘표준 프로토콜(MCP)’로 수렴 중**  
OpenAI가 Responses API에서 MCP를 언급하고, Anthropic도 MCP 최신 스펙(2026-07-28)을 빠르게 흡수합니다. 결과적으로, 툴 연동 레이어를 벤더별 SDK로 흩뿌리기보다 **MCP 같은 프로토콜 계층으로 분리**하는 쪽이 유지보수/이식성에서 유리해집니다(특히 정책/가격/레이트리밋 변동이 잦은 2026년엔 더).[^1]

---

## 💡 시사점과 전망
- **경쟁의 포인트가 “모델 스코어” → “에이전트 실행 플랫폼”으로 이동**  
Google은 Interactions API(서버 state)와 Managed Agents를, OpenAI는 Responses(도구 내장)를, Anthropic은 초대형 컨텍스트+MCP로 밀고 있습니다. 서로 방법은 달라도 “agentic workflow를 기본값으로 만든다”는 합의가 보입니다.[^3]

- **3~6개월 시나리오(가능성이 큰 순)**
  1) **Deprecation-driven migration 러시**: OpenAI Assistants API sunset(2026-08-26) 때문에 Q3 말~Q4 초에 마이그레이션 수요가 폭증할 겁니다.[^1]  
  2) **보안/거버넌스 강화가 과금만큼 중요해짐**: Google의 key restriction처럼 “안 하면 차단”류 정책이 타사에도 확산될 수 있습니다.[^4]  
  3) **프로토콜 기반 툴링(MCP) 채택 증가**: 에이전트가 붙는 시스템(사내 도구, SaaS, DB)을 표준화된 방식으로 노출하려는 요구가 커질 겁니다.[^8]

- **회의론/리스크도 분명**
  - 서버 state(예: Interactions API의 저장/이력)나 내장 도구 중심 API는 편하지만, **벤더 종속성과 디버깅 복잡도**가 같이 올라갑니다. “한 번의 호출로 multi-step”은 관측 가능성(observability)을 설계하지 않으면 장애 원인 파악이 더 어려워집니다.[^3]

---

## 🚀 마무리
핵심은 세 가지입니다. (1) OpenAI는 **Assistants API를 2026년 8월 26일에 종료**하며 Responses로 수렴, (2) Google은 **Gemini API key restriction을 강제**해 운영 표준을 끌어올림, (3) Anthropic은 **Sonnet 5(1M context) + MCP 최신 스펙**으로 에이전트 통합을 가속합니다.[^1]

개발자가 지금 할 수 있는 액션은 딱 2가지가 효율적입니다.  
1) OpenAI를 쓰고 있다면 **Assistants API 사용 지점을 전수 조사**하고, Responses API 마이그레이션을 “기능 개발”이 아니라 “리스크 제거” 트랙으로 분리해 2026-08-26 이전에 끝내세요.[^1]  
2) 멀티벤더/에이전트 툴 연동을 운영하는 팀이라면, SDK 호출을 흩뿌리기보다 **MCP 같은 프로토콜 계층으로 통합**하는 설계를 검토하세요(벤더 변경·정책 변경 시 비용이 급감합니다).[^8]
